Project Silent Echo — as of 17 Sep 2026, end of step 1e

Systems map

One pure engine, three renderers, an agent harness, and telemetry that doesn't exist yet. Dashed boxes are designed but not built — everything solid is real code checked into the repo today.

Building the eval harness

docs/EVALS.md is unusually thorough on methodology — more than most solo projects bother with. What it does not have is an implementation plan. Those are different documents, and right now only the first one exists.

What's actually defined spec exists

The Policy interface (chooseAction(view: AgentView): Promise<Action> | Action), the no-leakage rule for AgentView (no true map, no Wumpus position, no seed), the requirement that npm run sim and the LLM harness share one code path, fixed seed lists, full per-turn logging, and resumable batches — all specified. So is the scoring methodology: n=100 runs per policy (the doc does the confidence-interval math — n=20 gives you ±21pp, indistinguishable between a 35% and 50% model; n=100 gets you to ±9pp), three required baselines (random, a ~50-line heuristic bot, and 20 human runs on the shared seed set), one fixed prompt published verbatim, and one secondary condition (same models, plus a "reason about the tells" instruction) to report the delta on. The metrics to report beyond win rate are also listed: tame:fight ratio, SEND usage, deepest room reached and turn turned back, tell-ignored rate, Fortune spend timing, loss cause distribution, turns survived.

What isn't not yet defined

  • The AgentView adapter itself doesn't exist. legalActions already returns the right shape ({action, label, dc}), but the boundary that strips the true map and Wumpus position hasn't been written, and per the 1e session's own note, it needs a test proving it can't see through walls — that test doesn't exist either.
  • Which models, specifically. "How do I select specific models to try and escape" doesn't have an answer yet beyond the naming convention — a policy named llm:claude-sonnet-5 or llm:gpt-5 satisfies the interface, but nobody has picked the roster, and that's a real decision: how many models, which providers, whether it's one model family for a clean comparison or a spread for a more interesting leaderboard.
  • The API plumbing. Each llm:<model-id> policy has to actually call a model API — credentials, which SDK per provider, concurrency, rate limits, and retry/backoff (related to but not the same as the "resumable batches" requirement, which is about surviving a failure, not about how a live call is made).
  • Budget. n=100 runs × up to 20 turns × however many models × 2 conditions (baseline prompt + reasoning prompt) is a real number of paid API calls across possibly several providers. Nobody's sized this yet, and it's worth doing before, not after, running up a bill.
  • The prompt itself. EVALS.md says "fix the prompt and publish it verbatim" — the actual text doesn't exist yet.
  • The heuristic bot's ~50 lines — required as a baseline, not written.
  • The scoring/aggregation script that turns a batch of run logs into the report table above — not written. Nothing in scripts/ does this today; the closest things are tame.ts and turn.ts, which sweep the engine directly rather than score a stored batch of policy runs.

So: no, not everything is defined for 1g — the design is genuinely ready to build from, but "built to docs/EVALS.md requirements" (the roadmap's exit criterion) still leaves the adapter, the model roster, the API integration, the prompt text, the heuristic bot, and the scoring script as real work, not paperwork. The model roster and budget in particular aren't code decisions — they're calls only you can make, and probably worth settling before 1g starts rather than mid-session.
